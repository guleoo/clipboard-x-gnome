# 同步性能与压力测试指南

> 简体中文 · [English](sync-performance-testing.md)

本文说明插件同步的回归测试与受控回环网络测量，并区分已验证的行为，以及仍需单独验收的服务器互操作和 GNOME Shell 性能。

同步压力测试以固定的日常负载假设为基线，并且严格放大 10 倍。这里的数字是可审计的测试契约，不是用户行为统计；如果后续有真实遥测数据，应在评审中更新基线，而不是悄悄修改测试数字。

| 维度 | 日常基线 | 压力负载 |
| --- | ---: | ---: |
| 发布条目 | 200 | 2,000 |
| 入站变更事件 | 200 | 2,000 |
| 按需原文任务 | 20 | 200 |
| 进度更新 | 10,000 | 100,000 |
| 大对象快照 | 8 MiB | 80 MiB |

## 测试分层

- `sync-stress` 使用内存传输替身和独立、已持久化的文本条目，检查 2,000 个入站事件 ID、分页游标，以及共享同一个串行队列的 2,000 次发布与 200 个来源上传任务。替身读取真实来源字节，但不发送 HTTP 请求，也不将入站条目导入剪切板历史。传输状态、时间戳和待发送定时器都有上限；服务器确认完成的任务必须释放取消标记。
- 100,000 次进度更新按批次执行，并在批次间让出主循环。断言要求收到中间进度、字节数单调递增、精确的完成通知，以及完成后不再触发待发送回调。完全不发送通知不能通过测试。
- `sync-receive` 使用生产 `SyncClient`、传输替身和真实临时文件，覆盖本机文本/图片阈值、发送端策略不同、混合格式部分接收、等待来源设备、自动/手动请求复用、校验失败重试，以及历史重载后的完成状态。2,000 条接收突发负载验证串行下载和操作状态释放；它不是实际服务端或 GNOME Shell UI 性能测量。
- `sync-stream-stress` 启动仅监听 `127.0.0.1` 随机端口的临时 Python 标准库 HTTP 测试服务，使用生产 `HttpTransport`、`HttpClient` 和 libsoup 上传、下载实际写入磁盘的 80 MiB 模式数据。服务端检查认证头、接收字节数和 SHA-256；下载过程中保留旧目标文件，并通过独立的 `sha256sum` 验证最终落盘内容。测试服务每处理 64 KiB 暂停 1 ms，让测量获得多个采样点。
  该压力测试明确开启可选的 `sha256sum` 模式，不改变用户的默认配置。下载使用原生 GIO 流搬运，再由 `sha256sum` 从标准输入读取临时文件，校验成功后才替换目标。
- `sync-http-failures` 通过真实 HTTP 验证连接中断、哈希校验失败、下载及上传取消、请求体发送后的 HTTP 503、临时文件清理和显式重试。这是普通回归测试，不是 10 倍压力负载或自动重连测试。
  同时覆盖默认 GLib 与可选原生路径。原生路径还拒绝缺失/chunked 长度、压缩与超限声明；额外响应体测试验证 HTTP/1 Content-Length 对写盘的限制，并覆盖零字节内容和开始校验前取消。
- `sync-file-verifier` 验证二进制、特殊文件名、依赖查找、命令失败、异常/超长输出，以及取消后终止并回收子进程。`file-verification-settings` 验证开启必须等待依赖检查成功，失败、外部重置和关闭设置时不会保存未经检查的开启状态。
- `sync-measurement` 验证探针本身：故意在结束阶段阻塞 500 ms 必须能被发现；缺失、仅完成、倒退或总字节数错误的进度必须被拒绝。

## 测量指标与门槛

流式测试按上传、下载分别输出 JSON 记录：耗时、MiB/s、主循环采样次数、最大额外延迟、采样峰值 RSS 增量和 RSS 采样次数。

- 独立的测试服务线程每 5 ms 读取 GJS 进程的 `/proc/<pid>/status`，主线程阻塞时也能采样。上传、下载分别执行 **峰值 RSS 增量小于 64 MiB** 的预算检查。这是单次操作的采样预算，不是内存恒定或没有泄漏的证明。
- 10 ms GLib 定时器测量主循环额外延迟，操作结束后再等待一次采样才移除探针，避免漏掉结束阶段的阻塞。门槛为 **250 ms**，并要求至少两次主循环和 RSS 采样；这不是帧率保证。
- 每个方向的测量必须在 **30 秒**内完成。MiB/s 用于比较，不作为所有网络环境的通用速度要求。不要同时运行其他重型基准；Meson 不并行运行该流式基准与其他测试。

64 MiB 下载预算用于可选的 `sha256sum` 路径，不用于默认 GLib 路径。本机受控 80 MiB 实验中，即便先原生下载再用 GLib 校验文件，RSS 仍增加约 114 MiB。默认继续使用 GLib，是明确保留的零额外依赖取舍；这是已知内存限制，不是该模式通过预算的结果。低内存选项的压力门槛没有提高。使用流式 API 不意味着 GJS 会及时回收所有原生分配。

当前 RSS 探针只测量 GJS，不包含校验子进程。校验进程仅短暂运行并以原生块读取文件；此前独立原型采样的可执行程序 RSS 约 4.3 MiB，但这不是每次运行的自动预算检查，也不保证其他系统相同。原生下载请求 HTTP/1 和 identity 编码，拒绝没有受限、未压缩 Content-Length framing 的响应；该选项不会静默退回 GLib。

## 运行方式

运行压力套件（也包含剪切板历史压力测试）：

```sh
meson test -C build --suite stress --print-errorlogs
```

只运行两项同步压力测试：

```sh
meson test -C build sync-stress sync-stream-stress --print-errorlogs
```

运行探针和 HTTP 故障回归测试：

```sh
meson test -C build sync-measurement sync-http-failures --print-errorlogs
```

普通的 `meson test -C build` 也会执行这些测试。HTTP 测试服务需要回环 socket 权限、Python 3、Linux `/proc` 和 `sha256sum`。网络受限的沙盒需要明确允许访问回环网络；服务无法启动属于测试失败，不能视为跳过后通过。正常结束或抛出异常时，测试会清理临时文件并关闭 HTTP 进程。

## 通过测试不代表什么

10 倍基线是数量与大小契约，不是实测的用户事件到达速率。通过不能证明 2,000 个条目完整导入、生产服务器兼容、自动重连、任意未完成远端任务的总内存固定有界，或 GNOME Shell 界面流畅。只有服务器确认的终态才释放远端取消标记；未完成或尚未确认结束的本地失败任务保留标记，以便仍能取消，不受 UI 历史淘汰影响。

发布前仍需使用真实 `clipboard-x-server`，在嵌套或宿主 GNOME 中单独验收多设备混合操作、离线设备、慢网络/磁盘、配置变化和扩展关闭。
